# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Firmware for ESP32 boards that drive WS2812B/WS2811 addressable LED strips. The control path is **MQTT with Home Assistant discovery** — the device auto-registers as an HA `light` entity and is controlled via JSON command messages. **Palettes live outside the firmware**, in palette-service (homelab repo, `palette-service/`), which owns the palette library and each board's Palette `select` entity. Built with PlatformIO + Arduino framework + FastLED.

## Build / Upload / Monitor

PlatformIO is the toolchain. There are **multiple environments**, one per physical device, each selected with `-e`. There is no single "default" — always specify the environment.

```bash
pio run -e desk_esp32                    # compile
pio run -e desk_esp32 -t upload          # compile + flash over USB
pio run -e desk_esp32 -t upload -t monitor   # flash then open serial monitor
pio device monitor -b 115200             # serial monitor only (115200 baud)
pio run -t clean -e desk_esp32           # clean build artifacts
```

Environments (defined in [platformio.ini](platformio.ini)): `peg_esp32` (3 strips), `desk_esp32`, `wall_esp32`. Each also has an `*_ota` variant (e.g. `desk_esp32_ota`) that uploads over WiFi via ArduinoOTA/espota to the board's fixed LAN IP (`upload_port`; mDNS `.local` is unreliable on Windows); auth is injected from `OTA_PASSWORD` by [scripts/ota_auth.py](scripts/ota_auth.py). First flash must be USB. [scripts/fw_version.py](scripts/fw_version.py) (`[common]` `extra_scripts`) stamps `FW_VERSION` from `git describe --dirty`, published as the HA device's `sw_version`; an env that sets its own `extra_scripts` must keep `${common.extra_scripts}`. Each starts its `build_flags` with `${common.build_flags}` (FastLED's `MAX_LIKELY_UPDATE_RATE_HZ=200`: the boards run ~200-250 fps, so temporal dithering uses 2 bits, a 50-60 Hz cycle, instead of a visible 25-30 Hz shimmer in dim areas) and sets a `-DDEVICE_ID_ESP32_*` macro plus `LED_PIN_*` / `NUM_LEDS_*` / `LED_VOLTS` (LED supply voltage) build flags. Per-device identity (MQTT client/unique IDs, names) is resolved at compile time from that macro in [src/config/Config.h](src/config/Config.h); topic prefixes in [src/mqtt/MqttTopics.h](src/mqtt/MqttTopics.h) derive from `MQTT_CLIENT_ID`. **Adding a board = add an env block in `platformio.ini` and a matching `#elif` branch in `Config.h`** (and the strip-allocation block in [src/main.cpp](src/main.cpp)).

Unit tests run on the host (no hardware): `pio test -e native`. They cover only the pure-logic headers — [src/mqtt/HomeAssistantColor.h](src/mqtt/HomeAssistantColor.h), [src/led/ColorMath.h](src/led/ColorMath.h), [src/animation/AnimationDirection.h](src/animation/AnimationDirection.h), [src/animation/AnimMath.h](src/animation/AnimMath.h), [src/net/Version.h](src/net/Version.h), [src/net/ReleaseFormat.h](src/net/ReleaseFormat.h) — which must stay Arduino-free to remain testable. The `native` env excludes all firmware sources (`build_src_filter = -<*>`); a host GCC must be on PATH.

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs on every push: the native tests, plus a build of each board env on Linux (so filename case matters) **without** the credential headers, i.e. a release-style, secret-free build. **Adding a board means adding it to the workflow's matrix too.**

Releases come from [scripts/release.py](scripts/release.py), run on the PC with PlatformIO's Python (+ `cryptography`), never in CI: the ECDSA P-256 private key stays at `~/.esp32-led/release-signing-key.pem` (backup in Proton Drive `backup\esp32-led\`), its public half is [src/config/ReleaseKey.h](src/config/ReleaseKey.h). It builds every board from a clean header-free checkout at an annotated `vX.Y.Z` tag, signs `board/version/size/sha256` per image (the exact message format is in the script's docstring; firmware verification must reproduce it byte for byte), and publishes the images plus `manifest.json` as a GitHub Release. Its `BOARDS` map (env → `MQTT_CLIENT_ID`) needs a new board too. Always `--dry-run` first. **[docs/RELEASING.md](docs/RELEASING.md) is the full runbook** (setup on a new PC, steps, every refusal message and its fix, bad releases, key rotation): read it before any release work. The **user publishes** releases (Claude Code's permission check blocks creating public GitHub releases; hand over the command), and never run a `--dry-run` while they might be releasing (it holds the local tag for minutes).

Boards install releases themselves: [src/net/FirmwareUpdater.cpp](src/net/FirmwareUpdater.cpp) fetches the latest `manifest.json` over HTTPS (roots in [src/net/RootCAs.h](src/net/RootCAs.h), regenerate with `scripts/gen_root_cas.py` if GitHub changes CA), verifies the board's entry with mbedTLS against `ReleaseKey.h` using [ReleaseFormat.h](src/net/ReleaseFormat.h), and streams the image into the spare OTA slot, activating it only if size and SHA-256 match the signed values; [src/mqtt/UpdateEntity.cpp](src/mqtt/UpdateEntity.cpp) is the HA `update` entity around it (offers only `isNewerRelease()` per [Version.h](src/net/Version.h); installs run from `loop()`, never inside the MQTT callback). **Every new image boots on probation**: `verifyRollbackLater()` (must stay `extern "C"`, the core's weak default is C) stops the core auto-confirming it; reaching MQTT calls `FirmwareUpdater::markHealthy()`; otherwise after 10 min (or 3 boots) it rolls back — via the bootloader where it supports rollback (these boards' does: telemetry `ota_state` "pending"), else via the NVS slot record that `armProbation()` writes (called after every install and from ArduinoOTA `onEnd`). Keep `FirmwareUpdater::begin()` first in `setup()`. A test build with `PLATFORMIO_BUILD_FLAGS="-DFW_TEST_NEVER_HEALTHY -DFW_HEALTH_TIMEOUT_MS=90000UL"` exercises the rollback.

## Credentials (local headers → board NVS)

WiFi, MQTT and OTA settings live in each board's NVS storage ([src/config/Credentials.cpp](src/config/Credentials.cpp), `Preferences` namespace `creds`), which survives reboots and firmware updates. Two `.gitignore`d headers are their master copy — never commit them:

- `src/config/WifiCreds.h` — defines `WIFI_SSID`, `WIFI_PASSWORD`, `OTA_PASSWORD`
- `src/config/Mqtt.h` — defines `MQTT_SERVER`, `MQTT_PORT`, `MQTT_USER`, `MQTT_PASSWORD`

A build **with** them (any local build) uses their values and saves them to NVS when NVS differs, so one normal OTA upload provisions or updates a board. A build **without** them (CI, releases) compiles fine and uses NVS only, so the firmware file contains no secrets. Code reads the global `credentials` struct, never the macros (only `Credentials.cpp` includes the headers). Telemetry `creds_stored` shows whether a board's NVS holds a complete set (i.e. whether a header-free build would boot there). `scripts/ota_auth.py` still reads `OTA_PASSWORD` from the local header to authenticate uploads. Backups of the headers: Proton Drive `backup\esp32-led\config\`. To give a board away, erase its whole flash (`pio run -t erase`) — reflashing alone leaves NVS intact.

## Architecture

The control flow is a one-directional pipeline: **MQTT message → `MqttLight` (intent/state) → `LEDController` (per-strip ops) → `Strip` (state) → `Animation` (renders into the strip's `CRGB[]`) → `FastLED.show()`**.

- **[src/main.cpp](src/main.cpp)** — allocates the `CRGB[]` arrays statically (count/pins from build flags), registers strips with FastLED and the `LEDController`, wires up MQTT, and runs the loop. Chipset/color order is chosen per device (`WALL` = WS2811/RGB, others = WS2812B/GRB).

- **[src/mqtt/MqttLight.cpp](src/mqtt/MqttLight.cpp)** — the brain. Owns all user-facing state (power, brightness, hue/sat, selected effect, blend state). `loop()` runs every tick: handles MQTT reconnect, smoothly ramps brightness toward `targetBrightness`, and either drives the selected animation or renders a blended solid color. Key design points:
  - **Brightness is applied via `FastLED.setBrightness`, never as the HSV `V` channel** — solid colors are always rendered at full V. Brightness fades are time-based (`stepBrightnessRamp`, one step per `BRIGHTNESS_STEP_MS`), not one step per loop, so they don't depend on the frame rate.
  - Solid colours use CHSV's default conversion, `hsv2rgb_rainbow` (`LEDController::applyHsv`), on purpose: it spaces hues for LEDs, where green looks far brighter than red and blue. Standard HSV (`hsv2rgb_fullspectrum`) matches HA's picker numerically but looked wrong on the strips (reds orange, yellow greenish, green washed out); tried and reverted in Nov 2026.
  - Solid color changes **interpolate** hue (shortest path around the 255-wrap circle) and saturation over `solidBlendDurationMs` (~1s).
  - `callback()` parses HA JSON commands on `SET_TOPIC` (state/brightness/color/effect/`effect_dir`) and palettes on `PALETTE_DATA_TOPIC` (`{"name", "colors": [16 × "#RRGGBB"]}`; the name is reported back on `PALETTE_STATE_TOPIC`, "Custom" if missing or over 23 bytes).
  - On (re)connect it publishes HA discovery config (`publishDeviceConfig`), subscribes, publishes state, and announces itself to palette-service on the retained `PALETTE_BOARD_TOPIC` (`{"unique_id", "name", "palette"}`; after subscribing, since the service answers with the current palette's colors).
  - **State persistence:** the user-visible state (`SavedState` in [MqttLight.h](src/mqtt/MqttLight.h): on/off, brightness, hue/sat, effect, direction, palette name and its 16 colors) is saved to NVS (`lightstate` namespace) ~5 s after `markStateDirty()`, only when its bytes changed, and restored in `begin()` before MQTT. Any new user-facing setting must be added there (and to `captureState()`/`restoreState()`, bumping `STATE_VERSION` when the layout changes); call `markStateDirty()` wherever it changes. `flushState()` runs before deliberate reboots (ArduinoOTA `onStart`, HA installs).

- **[src/led/LEDController.cpp](src/led/LEDController.cpp)** — thin fan-out layer. Holds up to `MAX_STRIPS` (8) `Strip`s and applies every operation (clear, fill solid, animate, set palette/direction) across all of them. Stateless beyond the strip array + `isOn`.

- **[src/led/Strip.h](src/led/Strip.h)** — per-strip state struct: `leds` pointer + count, `currentPalette` (what animations read), `targetPalette`/`fromPalette` for palette changes, `direction`, and the active `Animation*`. A palette change crossfades over `LEDController::PALETTE_FADE_MS` (3 s, eased), advanced each frame in `LEDController::animate()` before the animations draw; animations never blend palettes themselves.

- **Animations** ([src/animation/](src/animation/)) — each implements the `Animation` interface (`update(Strip&)` + `getName()`). They are **singletons**: instantiated once in [AnimationRegistry.cpp](src/animation/AnimationRegistry.cpp), looked up by name, and write directly into `strip.leds`. One instance renders every strip, so per-strip variation must be keyed by `strip.id`. **Animations are pure functions of the shared clock** so boards stay in sync: [AnimClock](src/animation/AnimClock.h) is SNTP-synced epoch ms, latched once per frame by `LEDController::animate()`. Derive motion from `AnimClock::now()`, never from `millis()` or from accumulators integrated frame by frame — use `beatsinIntegral16` ([AnimMath.h](src/animation/AnimMath.h)) for the closed form of an `acc += deltams * beatsin88(...)` speed — and pass `AnimClock::timebase()` to every FastLED `beat*()`/`beatsin*()` call (they read local `millis()` otherwise). UI timing (palette crossfades, brightness fades) may stay on `millis()`. **Read palettes only through [PaletteSample.h](src/animation/PaletteSample.h)**: `paletteFolded(pal, phase16, bri)` walks a 16-bit phase there and back across the palette (`foldPhase16`, AnimMath.h, so it never wraps from the last colour to the first: palettes are written one-way), and `paletteAt(pal, index16, bri)` takes a 16-bit index up to `PALETTE_INDEX_MAX` (exactly the last entry). Both use `ColorFromPaletteExtended` (256 blend steps between entries, vs 16 for an 8-bit `ColorFromPalette` index, which visibly steps in slow motion) with video-style dimming. Keep the phases that drive them 16-bit too (e.g. `beat88`, `inoise16`), or the extra precision is lost. Compare timestamps as elapsed time (`now - start >= dur`), never absolute (`now >= start + dur`), so clock wraparound is safe. `NTP_SERVER` (build flag, default `pool.ntp.org`) picks the time server; telemetry's `clock_synced` shows whether a board has synced. The registry's `list()`/`getByName()` also feed the HA `effect_list`. **To add an animation: create the class, add the member + `animations[count++]` line in the registry constructor** (and bump `capacity` in [AnimationRegistry.h](src/animation/AnimationRegistry.h) if full).

- **Palettes** — the firmware keeps no palette library: it shows whatever palette-service sends on `PALETTE_DATA_TOPIC` and saves it (name + colors) in `SavedState`, so it survives reboots and service outages; only `RainbowColors` (the `Strip` default) is built in. palette-service publishes each board's Palette dropdown (`homeassistant/select/<MQTT_UNIQUE_ID>_palette/config`, the unique_id the firmware itself used before v1.3.0, so HA kept the entity) and resends the current palette when the board announces itself; `STATE_VERSION` 1 saved colors only for "Custom", so a v1 named palette restores as its name with default colors until that resend. **The palette topics are a contract with palette-service** (documented in its `main.py` docstring): change both sides together.

- **[src/mqtt/HomeAssistantColor.h](src/mqtt/HomeAssistantColor.h)** — conversions between HA's hue-degrees/sat-percent and FastLED's 0–255 hue/sat. Anywhere color crosses the MQTT boundary, it goes through these.

- **[src/net/NetworkManager.h](src/net/NetworkManager.h)** — static WiFi helpers: blocking `connect()` for setup() only; non-blocking, rate-limited `ensureConnected()` called every loop() tick so rendering survives WiFi drops.

## Conventions

- Device-specific behavior is handled with **compile-time `#if defined(DEVICE_ID_ESP32_*)` branches**, not runtime config. When touching anything device-specific, update every branch.
- Animations are registered in a single constructor ([AnimationRegistry.cpp](src/animation/AnimationRegistry.cpp)) — the registration choke point. Palettes are added in palette-service (`palettes.json` or saved from HA), never in the firmware.
- In `MqttLight::loop()`, `applyHsv` is guarded by the `prev*` caches (no redundant solid fills), but `show()` runs every loop on purpose: FastLED's temporal dithering only works if frames keep going out. Don't skip `show()` when nothing changed.
